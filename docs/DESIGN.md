# DESIGN.md
## 電話 × ChatGPT Live（OpenAI Realtime API）給湯器修理窓口デモ

最終更新: 2026-08-20（ヒアリング項目の変更を反映：住所廃止・区名ベース・営業エリア判定）
用途: 個人の実験・ポートフォリオ

---

## 1. 結論

- 構成: **Twilio Media Streams ↔ 自前WebSocketブリッジ ↔ OpenAI Realtime API**
- モデル: **`gpt-realtime-2.1`**（flagship。miniは数字認識の弱点があるため電話デモでは使わない）
- 実装の土台: **`twilio-samples/speech-assistant-openai-realtime-api-node`（またはpython版）をフォーク**。OpenAI公式サンプル(`openai/openai-realtime-twilio-demo`)は廃止済みモデル・旧仕様のままなので使わない
- 電話番号: 国不問。**Twilio US ローカル番号**（本人確認不要、即日取得可）
- ホスティング: **Cloudflare Tunnel + 常時起動サーバー**（開発中は開発者のMacでcloudflaredを起動、必要ならRender Starter $7/月等に後で移す）
- 想定コスト: 5分通話1回 約56円（Twilio+OpenAI）。50回テストで約3,000円（月額$1.15の番号代は別）
  - **注意: これに発信側の国際通話料が乗る**。iPhoneから直接掛けるとau 78円/分・docomo 68円/分で、50回テストなら17,000〜19,500円と**総額の85%以上を占める**。テスト段階はVoIP経由で`+1`に発信して回避する（findings-P0.md の P0-4 追記参照）

## 2. アーキテクチャ

```
iPhone (開発者) ──PSTN──> Twilio番号 (US Local)
                          │ TwiML: <Connect><Stream url="wss://<公開URL>/media-stream">
                          ▼
                 自前WSブリッジ (Node.js, twilio-samples fork)
                          │  g711_ulaw(8kHz) base64 双方向
                          ▼
                 OpenAI Realtime API (WebSocket, gpt-realtime-2.1)
                          │
                          └── function calling → ダミーDB/予約ロジック(ローカルJSON)
```

- ブリッジサーバーは開発者のMac上でローカル起動 → Cloudflare Tunnel で `wss://` を公開 → Twilioの着信番号のTwiML Webhookからこの公開URLへ`<Connect><Stream>`で接続
- 音声フォーマットは Twilio ⇄ OpenAI とも G.711 μ-law (8kHz) で統一。変換不要
- GA APIのセッション設定は以下のネスト形式（旧beta版のフラット`input_audio_format`は使えない）:

```js
session: {
  type: 'realtime',
  model: 'gpt-realtime-2.1',
  output_modalities: ['audio'],
  audio: {
    input: { format: { type: 'audio/pcmu' }, turn_detection: { type: 'server_vad' } },
    output: { format: { type: 'audio/pcmu' }, voice: VOICE },
  },
  instructions: SYSTEM_PROMPT,
}
```

## 3. シナリオ: 給湯器修理窓口サポート（架空メーカー）

**注意**: 実在メーカー名・実在エラーコードは使わない。架空の「〇〇給湯サービスセンター」とダミーのエラーコード体系で構成する。

### 会話フロー

図版は [README.md](../README.md) の「シナリオフロー」を参照（本節の記述と対で維持すること）。

1. 名乗り「〇〇給湯サービスセンターです」
2. 症状ヒアリング: お湯が出ない/ぬるい/エラー表示/異音/水漏れ
   - 危険ワード（ガス臭・煙・多量の水漏れ）は冒頭で毎回質問せず、発言から随時検知する（テンポを優先）
   - 水漏れ・異音・焦げ臭いを聞いた場合のみ、その場で程度を一度確認する
3. 機器特定: エラーコード、型番（言えない客が多い前提で設計）
4. 一次切り分け: ツール参照 → 応急処置で解決するものは案内して終話
5. 訪問予約: **訪問先の区名を聞く → `check_availability` で空き枠照会＋営業エリア判定 → 候補提示 → 氏名を聞く**
   - **住所は聞かない**（区名だけで足りる）。連絡先は発信者番号を自動利用するため原則聞かない
   - 営業エリアは**東京23区内のみ**。エリア内かどうかはAIに自己判断させず、`check_availability`の返り値`inServiceArea`に従わせる
   - `inServiceArea: false`（23区外・他都道府県）の場合は受付できない旨を案内し、予約フローに進まず終話する
6. 復唱確認: 予約確定直前に一度だけ、**日時・氏名**（電話番号を聞き取った場合はそれも）を読み上げる（項目ごとの都度復唱はしない）
7. 終話: 電話番号の下4桁で受付を伝え、訪問までの待機案内（`interimGuidance`）を一言添える（予約番号は発行しない）

**聞き取る項目は「区名」「氏名」「希望枠」の3つだけ。** 住所と電話番号を会話から外したのは、どちらもSTTが最も苦手な種類の入力だから。区名は選択肢が23個に閉じているぶん誤認識が起きにくく、営業エリアの判定にも足りる。

**終話は3経路（緊急エスカレーション後・受付完了後・営業エリア外）でサーバー側から能動的に切る。** Realtime API自体に通話を切る手段がないため、AIが応答を話し終えたこと（`markQueue`が空）を確認してからTwilio REST APIで切断する。

会話継続が不可能なエラー（OpenAI接続断）の場合は、AIに喋らせずサーバー側でストリームを閉じ、TwiML末尾の`<Say>`＋`<Hangup/>`で終話メッセージを流す。

**受付情報は永続化しない**（氏名・電話番号をファイル/DBに書き出さない。ログも電話番号下4桁のみ）。デモに不要な個人情報を保持しない方針。

### function calling ツール（すべてダミー実装）
| ツール | 引数 | 返り値 | 目的 |
|---|---|---|---|
| `lookup_error_code` | code | 症状名・原因候補・自己解決可否 | AIに数字を暗記させない |
| `check_availability` | area（東京23区の区名）, date_range | `inServiceArea` ＋ 空き枠リスト（`dateSpoken`付き） | 日程を勝手に確約させない／営業エリア判定をAIに委ねない |
| `book_visit` | name, slot_id（callback_phoneは任意） | 受付完了＋電話番号下4桁 | 確定処理 |
| `escalate_emergency` | reason | 応急案内＋転送の断り書き | 危険案件の離脱経路 |

### 意図的に用意する「難しい入力」（デモの見せ場）
- 型番が分からない客（「白い箱、としか…」）
- 話が脱線する客
- 途中で言い直す客（「20日…あ、やっぱり21日で」）
- AIの発話に被せて割り込む
- 「ガスの臭いがする」（緊急分岐の発火）

### システムプロンプトへの必須指示（P1-8調査の回避テクニック反映）
- 日程・在庫は**ツールの返り値以外を一切口にしない**。未確認時は「確認します」で止める
- **金額はいかなる場合も答えない**（概算・目安・「だいたい」も禁止）。どのツールも金額を返さないため、定型の断り文句を持たせて話を先へ進めさせる
- **日本語以外に切り替えない**。聞き取れなかった場合も日本語で聞き返す
- 重要情報（日時・氏名、聞き取った場合は電話番号）は**予約確定の直前に一度だけまとめて復唱確認**する（項目ごとの都度復唱はテンポを損なうため行わない）
- 営業エリアの判定は**AIに自己判断させず**、`check_availability`の返り値に従わせる
- 英語固有名詞・型番は**カタカナ表記**で与える
- 数字は**一桁ずつ区切って読む**よう指示する
- 応答は**簡潔に**（長い発話ほど音声が崩れやすい傾向）
- 危険ワード（ガス臭、煙、水漏れ多量等）検知時は即座に`escalate_emergency`を呼び、予約フローに進まない

## 4. 割り込み(barge-in)の実装方針

twilio-samplesの実装をベースに、以下の2段構えを維持する（`response.cancel`ではなくこちらが正しい実装):

1. OpenAIから `input_audio_buffer.speech_started` を受信
2. `conversation.item.truncate` をOpenAIに送信し、AIの発話済み範囲より先を切り詰める
3. Twilioに `{event: "clear", streamSid}` を送信し、送信済みでまだ再生されていない音声バッファを破棄する
4. `markQueue` で「AI音声が再生中かどうか」を追跡し、割り込み対象の有無を判定する

このロジックは壊さないこと。自作しない。
