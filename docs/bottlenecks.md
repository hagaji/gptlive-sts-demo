# 隘路事項（電話まわりの取得・運用）

最終更新: 2026-08-25

このプロジェクトで電話まわりに起因して詰まった点と、その回避策の記録。**検討して採らなかった経路も残す**（消すと同じ提案を再発明するため）。数値の出典は `findings-P0.md` / `findings-P2.md` にある。

## 【取り下げ】隘路1だったもの: Twilioトライアルでの `<Stream>` ブロック

**2026-08-25、実機で覆ったため隘路から取り下げた。** 記録として残す（同じ調査を繰り返さないため）。

当初の判定: 公式ドキュメント（`twilio.com/docs/usage/trials`）に「トライアルでは `<Stream>` verb がブロックされる」と記載があり、事実ならMedia Streams構成が成立しないため、**番号取得より先に有料化が必須**という結論を出していた。

**実測**: アカウント作成時のお試しクレジットの範囲で、**トライアルアカウントのまま `<Stream>` が動作した。** Media Streamsが確立し、OpenAI Realtime APIとの音声往復も成立している。有料化は行っていない。

**残る差分（2点、いずれも未解決）**:
1. **トライアル特有の英語警告アナウンス**は今も入る（こちらのTwiMLより前にTwilio側が挿入する "You have a trial account…" 相当）。実害はないがデモの体裁としては気になる。有料化で消えるはず
2. **検証できたのはVoice SDK（ブラウザ）経由のみ。** PSTN番号への着信で同じく `<Stream>` が動くかは**未検証**。元のドキュメント記述がPSTN経由を指していた可能性が残るため、番号取得後（Phase 5）に改めて確認すること

**教訓**: 一次情報に当たった上で、それでも実機と食い違った例。ドキュメントで「できない」と書かれていても、コストが低いなら試してから判断した方がよい。

**補足（別件・未確定事項）**: 日本在住個人がUS Local番号を取得できる根拠は、「USがRegulatory Bundle必須国のリストに含まれていない」という**消極的な確認**であって、「日本在住個人が取得できる」と明示した一次情報を見つけたわけではない。実際にConsoleで購入するまでは確定していない前提で進めること。

## 隘路2: Toll-Free番号は日本から掛からない

当初「Voice専用ならToll-Free検証が不要では」という観点で候補に挙げていた。検証不要は**正しかった**（Toll-Free verificationはSMS/メッセージング固有の要件）が、別の理由で使えない。

US Toll-Free（800/888/877等）が到達可能なのは**NANP圏内（米国・カナダ等）に限られる**。国外発信は不通か、通っても無料にならない。国際発信を丸ごとブロックしている番号も多い。

さらに、**Toll-Freeの唯一の利点「掛ける側が無料」が国外発信では消える**ため、月額（$2.15 vs $1.15）と分単価（$0.0220 vs $0.0085）が上がるだけで見返りがゼロになる。

**結論**: Localを使う。Toll-Freeが有効なのはデモを見せる相手が米国・カナダにいる場合のみ。

## 隘路3: 発信側の国際通話料が、本体コストを一桁上回る

**最も見落としやすかった項目**。当初の試算は「5分通話1回56円、50回で約3,000円」だったが、これはTwilioとOpenAIの分だけで、**掛ける側の国際通話料が一行も入っていなかった**。

| キャリア | 料金 | 分換算 |
|---|---|---|
| au | 39円/30秒 | 78円/分 |
| docomo WORLD CALL | 34円/30秒（昼） | 68円/分 |

50回 × 5分 = 250分で **17,000〜19,500円**。総額の85%以上が個人の携帯請求になる計算だった。

**回避**: テストはTwilio Voice SDK（ブラウザ）から発信する。**$0.0040/分**で250分あたり約150円。同じTwiMLアプリを経由するため経路は本番と同一で、Media Streamsに繋がり音声もμ-law 8kHzに落ちる。割り込み処理も同条件で発火するので、検証の忠実度は十分。

実機のiPhoneからのPSTN通話は、Phase 5の最終確認と録画に限定する。

## 隘路4: 日本の050番号は個人では取得できない

「発信側の通話料はかけ放題が効く050なら無料になる」という発想は正しい（かけ放題は050着信を対象に含む）。だが**取得資格で止まる**。

Twilioは日本の番号について**個人（individuals）へのNational（050）およびToll-Freeのバンドル提供を終了**している。公式の日本向け規制ガイドラインも "Requirements for Businesses" のみで、個人向けの経路が存在しない。

必要書類:
- 法人登記簿、事業所住所の証明、代表者の本人確認書類と住所証明
- **事業所住所と代表者住所の両方への、転送不可郵便による物理照合**

郵便照合の完了までバンドルはin-reviewのまま。リードタイムは**週単位**。

**結論**: 見送る。再検討する場合の最安経路は、**個人事業主の開業届で事業体要件を満たせるかをTwilioサポートに確認すること**（開業届は無料。法人登記まで必要かで難易度が大きく変わる。公式ドキュメントに記載がなく問い合わせないと判断できない）。

## 隘路5: 結果として「日本の人に自由に掛けてもらう」導線が無い

隘路2〜4の合成として、以下が同時に成立している。

- US Local番号は取れるが、日本から掛けると発信側に68〜78円/分かかる
- Toll-Freeにしても国外からは掛からない
- 050は個人では取得できない

つまり**「日本の相手に電話番号を渡して自由に試してもらう」が現状では塞がっている**。

**回避**: ブラウザから話しかけられるクライアント（Twilio Voice SDK）を用意する。国際電話も050も不要で誰でも触れる。

ただし公開すると**着信数だけOpenAIの従量課金が発生する**（1通話約56円）。ポートフォリオとしては録画を主役にし、ライブ版は限定公開かレート制限付きとするのが妥当。

## 検討したが採らなかった経路: OpenAI Realtime API の SIP 直収

Twilioを経由せず、SIPトランクをOpenAIのエンドポイント（`sip:{project_id}@sip.api.openai.com`）へ直接向ける構成が存在する。2025-08-28にGA化されており、廃止でもベータでもない。音声メディアが自前サーバーを通らないため、中継ホップが減りレイテンシ面では有利。

**採らなかった理由は可用性ではなく、切り分け可能性。**

メディアが自前サーバーを通らないということは、音声が途切れた・割り込みが効かないといった不具合が起きたときに、手元で観測できるものが何もないということでもある。ポートフォリオとして「何が起きているか説明できる」ことを優先し、音声バッファも割り込み処理も自分の手元を通るMedia Streams構成を選んだ。

Phase 5以降に余力があれば比較検証する価値はある。「SIPで十分では」という問いは自然に出るので、検討済みであることは残しておく。

## 隘路6: サーバー本体（server/index.js）は自動テスト化できない

`server/tools.js`・`tone.js`・`twiml.js`は入力→出力が決定的な純粋関数中心なので、`node:test`でユニットテスト化できた（`tools.test.js`・`tone.test.js`・`twiml.test.js`、計25ケース、`npm test`で一括実行）。実際、過去に見つけた `normalizeWardName` のバグ（「武蔵野市」が「武蔵野市区」になる）を意図的に再現させてテストが検知することも確認済み。

一方、`server/index.js` 本体は自動テスト化できない。理由は構造的なもの。

- **外部APIへの接続がハードコードされている**。OpenAI Realtime APIの接続先（`wss://api.openai.com/v1/realtime?...`）もTwilio REST APIクライアントも、モックに差し替える口がない。テスト可能にするには接続先を注入可能にするアーキテクチャ変更が前提になり、今回はそこまでのコストを払っていない
- **副作用の塊**。WebSocket接続の確立、タイマー（リンリンの1秒ギャップ、5分の強制切断）、Twilioへの能動的な通話終了API呼び出しなど、時間経過と外部状態に依存する処理が中心で、ユニットテストの対象として素直ではない
- **そもそも自動テストの対象外の領域がある**。音声品質、AIの応答の妥当性（プロンプトが効いているか、復唱確認を飛ばさないか）は、人間が実際に聞いて判断するしかない。これはテストコードの問題ではなく、音声AIというプロダクトの性質そのもの

**結論**: 純粋ロジック部分（tools/tone/twiml）はテスト化し、配線部分（index.js）は実接続での手動検証に頼り続ける方針。この切り分けを維持するため、今後index.jsに新しいロジックを足す際は、可能な限り純粋関数として別ファイルに切り出してからimportする形を優先する。
